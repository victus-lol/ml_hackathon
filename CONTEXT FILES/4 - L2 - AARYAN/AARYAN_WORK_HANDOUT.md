# PathSnap — Aaryan Work Handout

**Updated:** 18 November 2026  
**Owner:** Aaryan (distributed API/UI, candidate pipeline, model workflow)

## Work delivered

- Laptop 1 FastAPI API exposes health, trip discovery, and map-matching endpoints.
- Laptop 2 Streamlit/Folium UI requests trip IDs and predictions from the API and displays blue GPS observations with a red predicted route.
- The API accepts only a `trip_id`. It loads `.track`, `.nodes`, and `.arcs` on Laptop 1 and runs the candidate feature pipeline, trained classifier, and HMM/Viterbi decoder. It does not load `.route` labels during inference.
- The runtime loads `artifacts/experiments/final_model.joblib`; an Optuna-tuned alternative is also included.
- Training, tuning, decoder tuning, EDA, and report-generation scripts are included. Candidate tables are reproducible from the checked-in training and student-test inputs and are not committed.
- Five college handouts, 80 training trips, and 10 student-test trips remain in `reference_materials/`. No organizer-only evaluator partition is present.

## Data and deployment boundaries

- The development UI preview may point to `reference_materials/dataset/student_test`; health remains `ready: false` because the data kind is not `evaluator`.
- Organizer evaluator setup requires the permitted 10 raw trips on Laptop 1, with no `.route` labels in the API input folder.
- Health reports `ready: true` only when the model loads, `PATHSNAP_DATA_KIND=evaluator`, and exactly 10 trips are discoverable.
- The UI receives predicted geometry and raw GPS only. It does not open data files or reference labels.
- No two-laptop network check has been performed in this commit sequence. Testing is the next step after committing, as requested.
